# Pluto balance lab: Stage 2 paired trials

Status: the experiment planner, order-count parser and synthetic statistics have CI coverage. Native game launch and the first real Pluto match remain unexecuted.

## Native mod launch

Use the source-backed single-launch MPQDraft route. BWAPI's [MPQDraft instructions](https://github.com/bwapi/bwapi/blob/main/Release_Binary/MPQdraft/README.txt) specify LOAD MPQ PATCH, select StarCraft 1.16.1, select an MPQ, select BWAPI injector plugin, and finish. The [BWAPI plugin source](https://github.com/bwapi/bwapi/blob/main/bwapi/BWAPI_PluginInjector/mpqdraft.cpp) provides this integration. The Release Win32 project builds BWAPI_PluginInjector.qdp. Test it with a private copy and your Pluto v2.0 binary first, as described in [STAGE1_SMOKE.md](STAGE1_SMOKE.md).

The MPQ for each condition contains arr\flingy.dat, generated by the mod.py patcher and checked with preflight.py. Build separate control and devourer_speed_550 MPQs, and verify which one is actually loaded by an in-game speed measurement. The intervention is 5.00 to 5.50 pixels/game frame. Its effect on Pluto gameplay remains an open empirical question.

## Generate a balanced experiment

Copy [batch.example.json](batch.example.json) outside the Git repository and replace every example path with your private local path. The 30-pair setup requires:

- Two isolated copies of your legally obtained BW 1.16.1 installation, each with byte-identical StarCraft.exe, Pluto DLL, 64-bit inference executable, model weights and BWAPI config.
- Original-control and single-field treatment flingy.dat variants at different paths, with unequal SHA-256 hashes.
- One fixed map file.
- A valid Pluto v2.0 initial per-opponent bandit stats file, frozen before any batch experiment starts. Capture it from an initial baseline game and validate the file in Pluto before adopting it as the snapshot.

From the TensorCraft repository root:

    python -m starcraft_lab.batch plan --spec C:\BW-Lab\experiment.json --output C:\BW-Lab\runs\devourer_speed_v1

The planner creates a new run directory and refuses to overwrite it. It writes plan.json, bandit_baseline.txt, and 60 proposed manifests under manifests/. It never launches StarCraft, writes into game directories, or copies proprietary game binaries. Each manifest records exact hashes of engine, agent, inference binary, weights, config, map, mod and initial bandit data. Changing any of these invalidates the intended pairing.

The schedule randomizes order within balanced blocks and mirrors the planned A/B spawn assignment. The requested seed is a scheduler label until a launcher/observer proves control over the game's actual RNG. The spawn label is also only a plan until confirmed from the replay/map/launch record. Exact map and initial bandit hashes are both pinned.

## Run and collect evidence

For every planned entry, in assignment_index order:

1. Confirm that the correct game copy and correct MPQ have passed the Stage 1 loader, plugin and speed checks.
2. Before launching the game, restore the same bandit_baseline.txt bytes into the Pluto per-opponent bwapi-data/read/ and bwapi-data/write/ stats locations of the disposable game copy only. Back up any existing files before overwriting. Pluto reads whichever of read/write is newer; ensure both restored files carry the same frozen contents. Never reset a file while Pluto is running. Run just one game per install/opponent at a time.
3. Launch via MPQDraft, selecting the BWAPI injector plugin within MPQDraft. Ensure the opponent, player races, map and intended spawn are correct. Record which mod archive is actually loaded. Keep movement proof and native executable details with the private experiment.
4. Save the replay and copy the corresponding Pluto bandit log before the next game. Keep raw logs separate per run. Mark crash/timeout/incomplete replay as crash or unknown rather than as losses.
5. Edit a copy of that game's planned manifest with its actual result, result_evidence, result_evidence_sha256 and agent_player_id. Supply SHA-256 of the saved replay; agent_player_id comes from the parsed replay.
6. Run the pinned Rust parser and normalizer on that game's artifacts:

       cargo run --release --manifest-path starcraft_lab/replay_probe/Cargo.toml -- C:\BW-Lab\replays\RUN.rep C:\BW-Lab\parsed\RUN.json
       python -m starcraft_lab.telemetry record --manifest C:\BW-Lab\completed\RUN.json --pluto-log C:\BW-Lab\logs\RUN.txt --result-evidence-file C:\BW-Lab\replays\RUN.rep --replay-report C:\BW-Lab\parsed\RUN.json --output C:\BW-Lab\runs\devourer_speed_v1\records\RUN.json

The collector checks artifact hashes and compares the declared result to a first-leaver heuristic. The latter can fail for disconnections and unusual replay endings; it is not a tournament referee.

After collecting outcomes, analyze each balanced pair:

    python -m starcraft_lab.batch analyze --plan C:\BW-Lab\runs\devourer_speed_v1\plan.json --records C:\BW-Lab\runs\devourer_speed_v1\records

The report includes the treatment-minus-control difference in reported win outcomes and whether Pluto issued any Devourer morph orders. It calculates an exact two-sided sign test on discordant pairs and a seeded exploratory paired bootstrap interval. Any missing, mismatched or unbacked record is excluded with a reason. A pilot of 30 pairs is intended to find interesting hypotheses, not certify tournament balance.

## Interpretation limits

This first run uses a fixed self-play-trained model. Pluto's per-opponent opening bandit may adapt between ordinary games; restoring the frozen snapshot helps isolate the game's rule change. Modified Zerg stats are also available to the opposing Zerg in ZvZ, so the treatment acts on both sides. A changed win rate cannot alone establish the direction of the unit's strategic value.

Replay-core sees issued commands and models possible production starts. It cannot yet measure unit health, positions, energy, attacks, Acid Spores, survival, or confirmed completed morphs. The next instrumentation slice should record live unit state at regular frame intervals and confirm the effective Flingy speed, then add encounter-level kill/value exchange metrics.

Potential design follow-ups include shorter Devourer morph time, a cheaper Greater Spire path and Scout Tank-assassination scenarios. Run each as a separately registered one-mechanic experiment, preserving the control/baseline.
